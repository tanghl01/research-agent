# Skills

This directory stores skill manifests and local skill source caches exposed to
the Mastra workspace. The configured ACP execution agent can read these
registered skills through Mastra Workspace Skills when it handles user requests.

```text
skills/
  adapters/
    text-to-cad-cad.md
  manifests/
    GordenPPTSkill.skill.json
    guizang-ppt-skill.skill.json
    ppt-master.skill.json
    scientific-agent-skills.skill.json
    text-to-cad.skill.json
    claude-for-legal.skill.json
    industrial-leak-detection.skill.json
    industrial-meter-reading.skill.json
    Biomni.skill.json
  mastra/
    (virtual root exposed by apps/mastra/src/skills/operator-skill-source.ts)
  local/
    industrial-leak-detection/
    industrial-meter-reading/
  vendored/
    GordenPPTSkill/
    guizang-ppt-skill/
    ppt-master/
    scientific-agent-skills/
    text-to-cad/
    claude-for-legal/
    Biomni/
```

Rules:

- Vendored skill repositories live under `skills/vendored/<skill-id>/`.
- Operator-owned lightweight skills that are not external git repositories live under `skills/local/<skill-id>/` and are committed with the application.
- Skill ids and vendored directory names should match the original upstream repository name.
- Mastra-facing skill names should follow the Agent Skills convention used in `SKILL.md` frontmatter, such as `gorden-ppt-skill` and `guizang-ppt-skill`.
- `skills/mastra` is a virtual Mastra Workspace Skills root. It is served by Operator's `SkillSource`, which maps Mastra skill names to their original source repositories without copying those repositories into committed source.
- Collection repositories that do not have a root `SKILL.md` can be exposed through a virtual wrapper generated by `OperatorSkillSource`; the execution agent should still inspect the original README and relevant nested `SKILL.md` files before execution.
- A GitHub skill repository is the user-facing Mastra skill registration unit. A repository may be a single skill or a collection/package of nested skills, but the frontend should expose the project-level skill once.
- Collection repositories may declare nested execution units through manifest `subskills`. For example, `text-to-cad` exposes the upstream project once, while its `cad` subskill maps to `text-to-cad/skills/cad` and carries a Python runtime cache contract for the execution agent.
- Nested subskills are execution metadata for Codex and other main agents, not separate frontend tags unless the upstream project is intentionally split into multiple independent GitHub skill projects.
- Manifests may declare `execution.adapter_paths`. These Operator-owned adapter files are exposed as skill guidance after the upstream `SKILL.md` and before execution. Use adapters for skill-specific command order, validation gates, and known failure modes without editing the upstream repository.
- Manifests may declare `execution.agent_guard`. These are runtime guardrail declarations for capable execution agents or future Mastra middleware. Keep guardrails generic enough to apply to the skill, and put explanatory guidance in the adapter file.
- Every Operator skill must be installed through `pnpm capabilities:sync <skill-id> --kind skill` or `pnpm capabilities:sync --all --kind skill`. This is the mandatory capability lifecycle, not a source-only sync shortcut.
- Skill installation is owned by the broader Operator capability package lifecycle described in `docs/specs/Operator_Capability_Package_Spec.md`. There is no separate skill sync CLI or `packages/core/src/skills.ts` facade.
- The capability lifecycle must resolve or sync the source, validate required paths and entrypoints, validate required configuration, run declared runtime setup, run declared smoke tests and capability tests, run concrete registration/deployment gates, and write a capability receipt under `OPERATOR_CAPABILITY_INSTALL_STATE_ROOT` or `OPERATOR_RUNTIME_CACHE_ROOT/_capability-installs`.
- Runtime skill registration must require a successful, current install receipt. A skill whose install workflow failed, has no receipt, or has a stale receipt is unavailable to users even when its source files exist locally.
- Installation success is not enough for user availability. Any skill that claims model, image, search, database, browser, GPU, or external API capabilities must declare complete required configuration and pass a required capability test that reproduces an upstream example or Operator-maintained golden example before it can be exposed.
- Skill dependencies should be cached outside per-task workspaces through `OPERATOR_RUNTIME_CACHE_ROOT`. Task workspaces should contain generated source, artifacts, reports, and manifests, not reusable venvs or package caches.
- Python skills should keep independent venvs, while sharing pip download/build cache through `OPERATOR_PIP_CACHE_DIR` or the default `OPERATOR_RUNTIME_CACHE_ROOT/_pip-cache`.
- Manifests may declare `runtime` for reusable tool environments and `install` for required env vars and smoke tests. Do not rely on system Python/Node packages when the upstream skill needs repeatable dependencies.
- Skill-specific provider credentials must be mapped through manifest `runtime.commands` or runtime adapters, not global provider variables. For example, `ppt-master` maps `OPERATOR_PACKY_IMAGE_*` to OpenAI-compatible `OPENAI_*` names only for its `image_gen` child process.
- PPT skill execution does not live here and is not implemented as Operator-authored PPT workflows. The configured ACP agent reads the registered skill source through Mastra Workspace Skills and follows its `SKILL.md`.
- Deterministic Mastra workflows are reserved for stable system processes, such as `system.skill2workflow`, and for structured platform-owned flows where the output contract is fixed. The industrial daily monitoring report is implemented as a Mastra workflow because it compiles accepted leak findings and meter readings into a LaTeX/PDF report.
- External agent packages that are not Agent Skill repositories, such as `Biomni`, should be registered as scopes and manifests first, then promoted to a runtime integration only after the execution boundary is clear.
- External skills that should not be vendored should be referenced by manifest, URL, and commit/version instead of being copied into the repo root.
- `pnpm capabilities:sync --all --kind skill` installs every `agent_skill` and `agent_skill_collection` manifest, including local skills and git-backed skills. Deployment uses this discovery path, so new skills should not require editing the ECS sync list.
- `external_agent_package` manifests are intentionally excluded from `--all` unless `--include-external` is passed.
- New workflows should not add top-level repository directories.
